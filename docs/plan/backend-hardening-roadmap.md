# TripFlowAI 백엔드 견고성 4주 로드맵 & 포트폴리오 목차

> 목표 범위: **코드 견고성 위주** (배포 인프라 제외)
> 시간 예산: **4주 × 하루 2시간 (주 5일 = 주 10h, 총 ~40h)**
> 포트폴리오 초점: **Travelgram 메인** + travel_place 적재 + 임베딩 백필
> **핵심 철학**: *측정하지 않은 최적화는 하지 않는다.* 규모와 무관하게 **지금 아픈 것(실제 지연·실제 버그)**을 먼저 고치고, **규모가 커져야 의미 있는 최적화**는 "측정해서 판단·문서화"로 다룬다.

---

## 0. 이 로드맵이 한 번 갈아엎어진 이유 (중요)

처음엔 "벡터 인덱스, 배치 임베딩" 같은 **규모 의존 최적화**를 주 단위로 넣었다. 그런데 따져보니:

- 데이터가 **~1,000행, 일회성**이라 인덱스 없는 KNN도 `<1ms`, 행 단위 백필도 1초 안짝. **고칠 병목이 아니었다.**
- 이걸 "효과 있어 보이게" 하려면 **수 GB짜리 가짜 데이터**를 부어야 하는데, 그건 *최적화가 이 프로젝트의 진짜 문제가 아니라는 증거*다.

그래서 방향을 바꿨다. **"무조건 최적화"가 아니라 "측정→판단"**이 이 포트폴리오의 메인 서사다. (면접에서 "조기 최적화를 피하고 병목을 측정으로 찾았다"가 "닥치고 인덱스 박았다"보다 세다.)

## 2. 4주 로드맵

> 매일 2시간. 매주 **Day 1은 Before 측정, 마지막 날은 회고·포트폴리오 메모.** 측정 없는 변경은 포트폴리오가 안 된다.

### 🗓️ Week 1 — 사진 업로드 병렬화 + 바운디드 스레드풀 (진짜 성능)

**연결 CS**: 스레드 vs 프로세스, 스레드풀 사이징(I/O-bound), 병렬화로 `합 → max`, bounded queue·거부정책, 백프레셔, graceful shutdown

| Day | 작업 (2h) | 산출물 |
|-----|-----------|--------|
| 1 | Before 측정: 사진 10·20장 업로드 응답시간 (k6 `photo-upload-load.js` 완성해서 실측) | Before 수치 |
| 2 | `AsyncConfig`: 바운디드 `ThreadPoolTaskExecutor` 빈(core/max/queue/거부정책/이름). 풀 사이즈 근거 주석 | `config/AsyncConfig.java` |
| 3 | `uploadPhotosBatch` S3 업로드 **병렬화**(`CompletableFuture` + 풀, `allOf` 대기). `orderIndex` 보존, **부분 실패 정책**(전체 실패 vs 성공분 반환) 결정 | 병렬 업로드 |
| 4 | 메모리 가드(동시 업로드 수 = 풀 크기로 제한, 큰 파일 방어) + graceful shutdown | 안전장치 |
| 5 | After 측정(k6) + Before/After 표 + 포트폴리오 메모 | 비교 표 |

**검증**: 10·20장 업로드 응답시간이 `합산` → `최대 1장 수준`으로 떨어지는지, 큐 초과 시 거부정책 동작.

### 🗓️ Week 2 — 정합성 & 실제 버그 (규모 무관)

**연결 CS**: ACID, 트랜잭션 경계·전파, 상태 머신, 멱등성, at-least-once

| Day | 작업 (2h) | 산출물 |
|-----|-----------|--------|
| 1 | ★2 설계: `review_photos`에 분석 상태(`PENDING/READY/FAILED`) 도입. null=미완 암묵 규약 → 명시 상태 | 스키마 변경 설계 |
| 2 | 실패 시 `FAILED` 기록 + 재분석 엔트리포인트(수동 재시도 API 또는 스케줄) | 상태 전이 구현 |
| 3 | `createReview` 트랜잭션 경계 점검(post→group 2 insert + 역참조 update 한 트랜잭션). `@Async @Transactional`이 **별도 트랜잭션**임을 코드 주석+문서로 명문화 | 트랜잭션 정리 |
| 4 | 멱등성 정리: 네이버 임포트 `content_id` 해시 + `ON CONFLICT`를 "재실행 안전성"으로 문서화 | 멱등성 노트 |
| 5 | 회귀 방지 메모 + 포트폴리오 메모 | 회고 |

**검증**: 분석 강제 실패 주입 → `FAILED` 잔류 → 재시도로 `READY`. 동일 입력 2회 임포트 → 행 수 불변.

### 🗓️ Week 4 — "최적화 판단" (측정 후 대부분 보류) ★서사의 핵심

**연결 CS**: 측정·프로파일링, 병목 분석, **조기 최적화 회피**, (개념) 인덱스 자료구조·ANN, 분할상환

> 이 주는 "최적화 적용"이 아니라 **"측정해서 안 하기로 결정한 과정"**이 산출물이다.

| Day | 작업 (2h) | 산출물 |
|-----|-----------|--------|
| 1 | 벡터검색 `EXPLAIN ANALYZE` @1,000행(빠름 확인) + 크로스오버 실험 설계 | Before 측정 |
| 2 | 합성 벡터(SQL `generate_series`+random, `halfvec`) 10만행 생성 → 인덱스 전/후 측정 → **"~10만행부터 이득, 우리는 1,000행 → 미적용"** 결론 문서 | 크로스오버 분석 |
| 3 | 백필 배치 분석: DB `batchUpdate`는 무의미(<1초), 임베딩 호출 배치만 유의미함을 측정으로 제시 | 배치 분석 문서 |

| 5 | 전체 회고: "측정 → 판단" 표 + 리팩토링↔CS 매핑 + 포트폴리오 마무리 | 회고 표 |

## 3. 포트폴리오 목차

> 스토리라인: **"동작하는 코드를, 측정으로 진짜 문제를 가려내 운영급으로 끌어올린 과정. 그리고 안 해도 되는 최적화는 측정으로 걸러낸 판단력."**

```
1. 프로젝트 개요 (TripFlowAI · 역할 · 스택 · 다룰 3축)

2. [메인] Travelgram — 여행 기록 생성 파이프라인
   2.1 플로우 (리뷰 생성 → 사진 업로드 → AI 분석 → 스타일/해시태그/캡션)
   2.2 API 컨트랙트 표
   2.3 ★ 진짜 병목: 사진 일괄 업로드가 순차 S3 전송 → 사용자 합산 대기
       - 프론트가 한 요청에 N장 묶어 보냄(근거) → 서버 for 루프가 병목
       - 해결: 바운디드 스레드풀 + 병렬 업로드 (합 → max)
       - Before/After(사진 10·20장 응답시간), 부분 실패 정책
       - CS: 동시성, 병렬화, 스레드풀 사이징, 백프레셔   ← [W1]
   2.4 ★ 실제 버그: 분석 실패 시 summary null 영구 방치 → 상태 머신 + 재시도
       - CS: 상태 머신, 멱등성, @Async와 트랜잭션 경계     ← [W2]
   2.5 테스트로 굳히기: 외부(OpenAI/S3) 모킹, 무엇을/왜 모킹했나  ← [W3]

3. travel_place 적재 — 네이버 로컬 검색 임포트
   3.1 왜 필요 (추천 후보 풀)
   3.2 멱등 업서트: SHA-256 content_id + ON CONFLICT (재실행 안전)  ← [W2]
   3.3 내결함성: 외부 API 실패 재시도 (swallow 제거)              ← [W4]

4. 임베딩 백필 & 벡터 검색 — "측정해서 안 한 최적화"
   4.1 왜 임베딩인가 (의미 검색)
   4.2 ★ 측정 기반 판단 (이 포트폴리오의 차별점)
       - 벡터 인덱스: 1,000행에선 seq-scan도 <1ms. 합성 데이터로 크로스오버(~10만행) 측정 → 미적용 결정
       - 3072차원의 함정: pgvector 인덱스 2000 한계(스키마 증거: 1536만 인덱스됨)
       - 배치: DB batchUpdate는 <1초라 무의미, 임베딩 호출 배치만 유의미 — 측정으로 판단
       - CS: 측정·프로파일링, 조기 최적화 회피, ANN/인덱스 자료구조  ← [W4]

5. 회고 — 리팩토링 ↔ CS 매핑 표 (작업 / 전·후 / 근거 CS / 측정값 / 적용·보류 판단)

6. 한계와 다음 단계 (보안 시크릿 외부화 · 배포 · 관측성 · 규모 커질 때의 인덱스/배치)
```

## 4. 진행 원칙 (매주 반복)

1. **측정 먼저.** Before 수치 없으면 손대지 않는다.
2. **"안 하기로 한 것"도 산출물이다.** 측정 근거와 함께 기록한다.
3. **변경 1건 = 커밋 1개 + 근거 한 줄.**
4. **레이어 경계 유지** (Controller→Service→Repository).
5. **하루 2시간 사수.** 새 이슈는 "다음 단계"에 적고 넘어간다.
