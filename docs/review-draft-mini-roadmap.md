# Review Draft Mini Roadmap

> 목표 범위: 리뷰 초안 생성 흐름의 중복 요청 방지, AI 실패 처리, 응답시간/token usage 로깅
> 예상 시간: 총 6~10시간, 하루 2시간 기준 3~4일
> 원칙: 큰 구조 변경보다 현재 흐름을 먼저 측정하고, 실패와 중복을 명확히 다룬다.

---

## 1. 왜 4주 로드맵에서 따로 뺐나

기존 4주 로드맵은 백엔드 견고성 전체를 다룬다. 하지만 지금 프로젝트 포커스는 리뷰 초안 생성 흐름에 더 가깝다.

리뷰 초안 생성은 AI 호출이 들어가는 흐름이라 다음 문제가 먼저 중요하다.

- 사용자가 버튼을 여러 번 눌렀을 때 중복 AI 호출이 발생할 수 있는가
- AI 호출 실패 시 DB나 응답 상태가 애매하게 남는가
- 응답시간과 token usage를 기록해서 이후 개선 근거로 쓸 수 있는가

따라서 사진 업로드 병렬화나 벡터 검색 최적화보다 먼저, 리뷰 초안 생성 흐름만 작은 스프린트로 분리한다.

---

## 3. 미니 로드맵

### Day 1 - 리뷰 초안 생성 흐름 분석

예상 시간: 1~2시간

목표:

- 프론트에서 어떤 이벤트로 리뷰 초안 생성을 요청하는지 확인
- 백엔드에서 어떤 Controller, Service, Repository를 타는지 확인
- AI 호출 전후에 어떤 데이터가 저장되는지 확인
- 현재 실패/중복/로깅 처리가 어디까지 되어 있는지 확인

산출물:

- call flow 정리
- 관련 파일 목록
- 현재 위험 지점 목록

검증 기준:

- 요청 시작점부터 AI 응답 저장/반환까지 한 줄 흐름으로 설명할 수 있어야 한다.

---

### Day 2 - 중복 요청 방지 최소 구현

예상 시간: 2~3시간

목표:

- 같은 리뷰 또는 같은 초안 생성 대상에 대해 중복 AI 호출이 발생하지 않게 한다.
- 프론트 loading/disabled 처리와 백엔드 상태 체크 중 현재 코드에 더 작은 변경을 선택한다.
- public API contract 변경은 피한다. 꼭 필요하면 먼저 별도 판단한다.

가능한 구현 방향:

- 이미 생성 중이면 새 요청을 막는다.
- 이미 생성 완료된 초안이 있으면 기존 결과를 반환한다.
- 프론트 버튼 중복 클릭만 문제라면 우선 loading 상태로 막는다.

산출물:

- 중복 요청 방지 구현
- 중복 클릭 또는 중복 요청 수동 검증 결과

주의점:

- 단순 버튼 disable만으로는 네트워크 재시도나 직접 API 호출 중복을 막지 못한다.
- 백엔드 상태 체크를 넣는 경우 동시 요청 race condition 가능성을 확인해야 한다.

---

### Day 3 - AI 실패 처리 명확화

예상 시간: 2~3시간

목표:

- AI 호출 실패가 null, 빈 문자열, 로그만 남는 상태로 끝나지 않게 한다.
- 실패한 대상과 실패 원인을 추적 가능하게 한다.
- 재시도 API는 바로 만들지 않고, 먼저 실패 상태를 명확히 남기는 데 집중한다.

가능한 구현 방향:

- 실패 시 `FAILED` 상태 저장
- 성공 시 `READY` 또는 이에 준하는 완료 상태 저장
- 진행 중 상태가 필요하면 `PENDING` 사용
- 로그에 review/post id, 요청 id, 실패 원인을 포함

산출물:

- 실패 상태 처리 구현
- AI 실패 강제 상황에서의 결과 확인

주의점:

- 실패를 숨기고 성공 응답처럼 반환하면 프론트가 잘못된 화면을 보여줄 수 있다.
- `@Async` 흐름이면 요청 트랜잭션과 AI 처리 트랜잭션이 다를 수 있다.

---

### Day 4 - 응답시간 및 token usage 로깅

예상 시간: 1~2시간

목표:

- AI 호출 시간이 얼마나 걸리는지 기록한다.
- 사용 가능한 경우 input/output/total token usage를 기록한다.
- 이후 최적화나 비용 판단의 근거를 만든다.

가능한 구현 방향:

- AI 호출 시작/종료 시간 측정
- 성공/실패 여부와 elapsed time 로깅
- token usage가 응답 객체에 있으면 함께 로깅
- DB 저장은 필요성이 확인된 뒤 별도 작업으로 분리

산출물:

- 응답시간 로그
- token usage 로그
- 성공/실패 케이스 로그 예시

주의점:

- prompt 원문이나 사용자 민감 정보는 로그에 남기지 않는다.
- token usage가 제공되지 않는 모델/클라이언트라면 unavailable로 명확히 남긴다.

---

## 4. 완료 기준

이 미니 로드맵은 다음이 가능하면 완료로 본다.

- 리뷰 초안 생성 요청 흐름을 파일 단위로 설명할 수 있다.
- 중복 요청이 어디서 막히는지 설명할 수 있다.
- AI 실패 시 어떤 상태와 로그가 남는지 확인할 수 있다.
- AI 호출 응답시간과 token usage 확인 방법이 있다.
- 변경 범위가 리뷰 초안 생성 흐름에 한정되어 있다.

---

## 5. 4주 로드맵과의 관계

이 문서는 기존 `backend-hardening-roadmap.md`의 대체가 아니라 선행 작업이다.

추천 순서:

1. 이 미니 로드맵으로 리뷰 초안 생성 흐름을 먼저 안정화한다.
2. 이후 사진 업로드 병렬화와 분석 실패 상태 머신을 기존 4주 로드맵에서 이어서 진행한다.
3. 벡터 인덱스와 임베딩 백필은 측정 결과를 보고 보류 또는 적용을 판단한다.
