# 작업로그 — 01. 리뷰 입력 데이터 정비

> 형식: 배경 / 작업 / 결과 / 회고
> 메모: 공개용 문서라서 내부 구현의 세부 디테일보다는 흐름과 판단 중심으로 정리한다.

---

## 배경

리뷰 생성을 안정적으로 만들려면, 먼저 여행 계획과 장소 데이터가 충분히 채워져 있어야 했다.  
기존 장소 데이터만으로는 리뷰 생성에 필요한 품질과 일관성이 부족해서, 장소 수집 방식을 정비했다.

## 작업

- 스키마 정리
  - `schema.sql`을 기준으로 주요 테이블 구조를 정리했다.
  - 구조화된 문서나 배열 데이터를 담는 컬럼에는 `jsonb`를 사용했다.
    - `travel_places.tags`: 태그 배열을 저장하고, 나중에 태그 기준 필터링이 가능하도록 설계
    - `hotel_bookings.provider_booking_meta`: 예약 부가정보를 구조화된 형태로 저장
    - `ai_review_analysis.input_json`, `output_json`: AI 요청/응답 원문을 유연하게 보관
    - `plan_snapshots.snapshot_json`: 여행 계획 전체를 버전 단위로 저장

- 장소 데이터 확보
  - 데모용 seed 데이터를 먼저 준비하고, 임베딩이 비어 있는 데이터는 백필로 채우는 흐름을 구성했다.
  - 리뷰 생성용 입력 품질을 높이기 위해 장소 수집 소스를 네이버 Local Search 기반으로 전환했다.
  - 네이버 응답에는 고유 ID가 없어, 장소명과 주소를 조합해 해시 기반의 중복 키를 만들었다.
  - 같은 이름이나 표기 차이로 중복이 발생할 수 있는 점은 한계로 남아 있다.

- import / backfill 실행 구조 분리
  - 서버 시작 시 한 번 실행하는 경로와, 필요할 때만 주기적으로 실행하는 경로를 분리했다.
  - 임베딩 백필은 기존 데이터 보정용으로 남겼다.
  - 관리용 배치 작업이라 MyBatis보다 단순한 JDBC 기반 처리로 구성했다.

- 네이버 설정 정리
  - 네이버 API 인증 정보와 import 실행 설정을 분리했다.
  - 인증 정보는 공통 설정으로 두고, import 관련 옵션은 별도 설정으로 관리했다.
  - 읽기 전용 성격이 강한 설정은 record 기반 properties로 정리했다.

- 호텔 관련 정리
  - 호텔 예약 데이터 저장 과정에서 `providerBookingMeta`를 JSON으로 직렬화하도록 수정했다.
  - 프론트에서는 서버가 생성한 메타데이터를 다시 전송하지 않도록 정리했다.
  - 예약 저장 시 `providerBookingMeta`가 비어 있어도 실패하지 않도록 null-safe 처리를 추가했다.
  - 호텔 예약 요약 조회는 별도 요약 매퍼로 정리했다.

## 결과

- 리뷰 생성에 필요한 입력 데이터 흐름을 확보했다.
- 장소 데이터는 중복 관리가 가능해졌고, 재실행에도 비교적 안전한 구조가 되었다.
- 네이버 기반 수집, 임베딩 백필, 호텔 예약 저장 흐름이 각각 역할별로 분리되었다.

## 회고

- 작업 범위가 쉽게 넓어질 수 있어서, 처음 목표를 벗어나는 기능은 다음 작업으로 분리하는 편이 낫다.
- 데이터 수집과 저장 구조를 바꾸는 작업은 구현보다 검증 비용이 크므로, 변경 범위를 작게 유지하는 것이 중요하다.
- AI나 외부 API를 붙일 때는 기능 구현 자체보다, 어떤 데이터가 실제로 필요한지 먼저 정리하는 게 우선이다.
